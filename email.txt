================================================================================
  CENTRAL EMAIL SYSTEM — HOW TO CONNECT A NEW PROJECT
  Give this file to any new project. It is all you need.
================================================================================

  LIVE GATEWAY   https://email-services-nu.vercel.app
  DASHBOARD      https://email-services-nu.vercel.app          (quota, queue, log)
  HEALTH         https://email-services-nu.vercel.app/api/v1/health
  SOURCE         https://github.com/mshraky3/email-services
  SENDING DOMAIN smle-question-bank.com   (verified with Resend)

  Already connected: medqize (SQB), hr, portfolio, game.
  Ask the admin for your project's own key — never reuse another project's.

WHAT THIS IS
  One service that sends email for every project. You do not install a mail
  library, you do not hold an API key for a mail provider, you do not write
  SMTP config. You POST JSON to the gateway and it decides how and when to send.

THE ONE HARD RULE
  Never send email any other way. No nodemailer, no SMTP, no Resend SDK inside
  your project. Every project sends from ONE verified domain on ONE free plan,
  so a project that sends behind the gateway's back breaks the budget for
  everyone and damages a sending reputation that all projects share.

HOW IT SENDS
  Immediately. You POST, the email goes out, you get the real result back with
  the provider's message id. There is no queue, no scheduler and nothing to
  poll. A 200 means it left the building.

THE BUDGET
  Resend free tier = 100 emails/day across ALL projects combined. The gateway
  uses 95 to leave headroom, and that is the ONLY quota rule:

    under 95 today  ->  sent via Resend, on the verified domain
    at or over 95   ->  sent via Gmail instead (separate 500/day allowance)

  Nothing is ever refused, delayed or dropped because of quota. Gmail is a
  fallback, not a plan: it is unauthenticated for this domain and more likely
  to land in spam, so it exists purely so mail never stops.

--------------------------------------------------------------------------------
1. GET REGISTERED
--------------------------------------------------------------------------------
Ask the gateway admin (that's you) to register the project:

  curl -X POST https://email-services-nu.vercel.app/api/admin \
    -H "Authorization: Bearer $ADMIN_KEY" \
    -H "Content-Type: application/json" \
    -d '{
      "action": "create_project",
      "slug": "myapp",
      "display_name": "My App",
      "from_local_part": "myapp",
      "default_from_name": "My App",
      "default_locale": "ar",
      "default_dir": "rtl",
      "best_priority": 1,
      "daily_max": 30,
      "production_origins": ["myapp.com", "myapp.vercel.app"]
    }'

You get back an API key ONCE:

  { "ok": true, "api_key": "ek_live_myapp_xxxxxxxxxxxx", "key_prefix": "..." }

Store it now. It is only ever shown at creation. Lost keys are rotated, not
recovered.

  from_local_part   your mail arrives as  myapp@smle-question-bank.com
  best_priority     the BEST priority you may request. Leave at 1 unless the
                    project genuinely has a blocking flow (OTP / password reset).
  daily_max         hard per-project cap. A runaway loop in your project eats
                    at most this much of the shared budget, never all of it.
  production_origins  YOUR REAL HOSTNAMES. Mail arriving from anywhere else is
                    DROPPED as dev traffic (see section 8). Forget this and
                    every email you send disappears silently. You can set it
                    later without redeploying the gateway:

                      curl -X POST https://email-services-nu.vercel.app/api/admin                         -H "Authorization: Bearer $ADMIN_KEY"                         -H "Content-Type: application/json"                         -d '{"action":"set_origins","slug":"myapp",
                             "production_origins":["myapp.com"]}'

--------------------------------------------------------------------------------
2. TWO ENV VARS + ONE FILE
--------------------------------------------------------------------------------
In your project's .env (gitignored):

  EMAIL_GATEWAY_URL=https://email-services-nu.vercel.app
  EMAIL_GATEWAY_KEY=ek_live_myapp_xxxxxxxxxxxx
  EMAIL_GATEWAY_MODE=on

Copy ONE file into your project — no npm install, no build step:

  email-system/packages/email-client/email-client.js  ->  services/email-client.js

Wire it up:

  import { createEmailClient } from './services/email-client.js';

  export const mail = createEmailClient({
    baseUrl: process.env.EMAIL_GATEWAY_URL,
    apiKey:  process.env.EMAIL_GATEWAY_KEY,
    mode:    process.env.EMAIL_GATEWAY_MODE,   // 'off' | 'shadow' | 'on'
  });

--------------------------------------------------------------------------------
3. REGISTER YOUR EVENT TYPES
--------------------------------------------------------------------------------
Every email your project sends needs a policy row. This is where priority,
audience and digesting are decided — NOT in your code. Your code names an
event; the gateway decides what that means.

  curl -X POST https://email-services-nu.vercel.app/api/admin \
    -H "Authorization: Bearer $ADMIN_KEY" -H "Content-Type: application/json" \
    -d '{
      "action": "set_policy",
      "slug": "myapp",
      "event_type": "myapp.otp.login",
      "priority": 0,
      "audience": "user",
      "delivery_mode": "immediate",
      "honors_unsubscribe": false
    }'

Fields that matter:

  audience        "user" | "owner" | "internal" — who the mail is for.
  cooldown_seconds  swallow identical repeats for this long. Set it on error
                    alerts (900 is a good default) and pass a stable dedupeKey,
                    and one broken endpoint sends ONE email instead of forty.
                    Leave it 0 for everything a person is actually waiting for.
  honors_unsubscribe  set FALSE for OTP and invoices. Nobody can unsubscribe
                    from their own password reset.
  transport_hint  force "gmail" or "resend". Rarely needed — leave it null.
  priority        only grades suppressions: 0-1 survive an unsubscribe,
                  3+ is marketing and does not.

An UNREGISTERED event still sends — it just gets cautious defaults (P2,
immediate). Register it anyway; the defaults are not what you want.

--------------------------------------------------------------------------------
4. SENDING — PICK A TIER
--------------------------------------------------------------------------------

TIER C — you have no template (START HERE if the project is new)
  The gateway renders it. You never write email HTML, and you get correct
  RTL Arabic for free.

    await mail.send({
      event: 'myapp.otp.login',
      to: user.email,
      template: 'otp',
      data: { code: '4821', minutes: 5 },
      idempotencyKey: `otp:${user.id}:${code}`,
    });

  Templates: 'otp' (a code) and 'notice' (heading + body + optional button).

TIER B — an event that should be BUNDLED (all owner-facing mail)
  You send structure, not HTML, because the gateway may merge this with other
  events into one digest email. You cannot merge rendered HTML.

    await mail.notify({
      event: 'myapp.owner.new_signup',
      to: OWNER_EMAIL,
      title: 'New signup',
      summary: 'ahmed@example.com joined',
      severity: 'info',                 // 'info' | 'warn' | 'critical'
      fields: [{ label: 'Plan', value: 'Free' }],
      link: { label: 'Open in admin', url: 'https://myapp.com/admin/users/91' },
      dedupeKey: 'myapp.signup',
      sourceOrigin: req.headers.referer,
    });

TIER A — you already have rendered HTML
  For existing projects with templates that already work. The gateway adds the
  correct From, Reply-To and unsubscribe headers, and changes nothing else.

    await mail.send({
      event: 'myapp.invoice',
      to: user.email,
      subject: 'فاتورتك',
      html: renderedHtml,
      text: plainTextVersion,          // always include one: spam filters score it
      attachments: [{ filename: 'invoice.pdf', content: pdfBase64,
                      content_type: 'application/pdf' }],
      idempotencyKey: `invoice:${invoiceNumber}`,
    });

--------------------------------------------------------------------------------
5. READ THE RESPONSE PROPERLY — THIS IS THE PART PEOPLE GET WRONG
--------------------------------------------------------------------------------
  200 {"status":"sent"}        gone out. provider_id tells you which message.
  200 {"status":"suppressed"}  that address bounced, complained or unsubscribed.
  200 {"status":"dropped"}     non-production origin (see section 8).
  200 {"status":"throttled"}   an identical alert went out moments ago.
  200 {"status":"duplicate"}   this idempotency key already sent.

  400 / 413                    your payload is wrong. Fix it; do not retry.
  502 {"status":"failed"}      the gateway tried and the transport refused.
                               It is parked and retried automatically.
  500 gateway_unavailable      the gateway itself is down.

  Every 200 is a SUCCESS, including the four that did not send an email. They
  are decisions the gateway made on purpose. Do not retry them, and do not
  send the message some other way to get around them — "suppressed" in
  particular means mailing that address damages a reputation every project
  shares. (The supplied client already implements this. Use it.)

--------------------------------------------------------------------------------
6. WHAT THE GATEWAY DECIDES FOR YOU
--------------------------------------------------------------------------------
  Everything sends immediately, so there is no waiting to reason about. What
  the gateway still decides:

  IT WILL NOT SEND to an address that hard-bounced or reported spam. All
  projects share one domain and one reputation; mailing a dead address hurts
  delivery for everyone.

  IT WILL NOT SEND mail whose origin is not one of your registered production
  hostnames — see section 8. This is the localhost guard.

  IT WILL NOT SEND an identical alert twice inside your event's cooldown.

  IT WILL NOT SEND twice for the same idempotencyKey.

  IT WILL SWITCH to Gmail if the day's Resend budget is gone, rather than
  refusing. You do not have to handle that case.

 RULES FOR NOT BREAKING THINGS
--------------------------------------------------------------------------------
  DO NOT loop over recipients calling send(). Use sendBulk():

    await mail.sendBulk({
      event: 'myapp.announcement',
      subject: 'إعلان',
      html: body,
      priority: 4,
      recipients: ['a@x.com', { to: 'b@x.com', toName: 'Sara' }],
    });

    -> 202 { batch_id, accepted: 2, capacity_today: 40, scheduled_over: "today" }

  ALWAYS pass an idempotencyKey on anything money- or account-related. It is
  what stops a retry, a double-click or a re-run from sending twice.

  CHECK THE BUDGET before a big batch, if you would rather not spill onto the
  Gmail fallback:

    const q = await mail.quota();
    if (q.remaining < rows.length) { /* send fewer, or accept the fallback */ }

  This is advisory. Nothing is refused when the budget runs out.

  ALWAYS send a plain-text part alongside HTML. It measurably improves
  deliverability, and all four existing projects already do it.

  ATTACHMENTS: base64, max 2 MB per message and 3 MB per request. Above ~1 MB
  host the file yourself and pass { filename, url } instead.

--------------------------------------------------------------------------------
8. THE ORIGIN GATE (why your dev machine stops emailing you)
--------------------------------------------------------------------------------
Running a frontend on localhost against the PRODUCTION backend used to fire
real error emails — every dev-session stack trace landing in the inbox and
burning shared quota.

Pass the request origin and the gateway drops anything non-production:

    sourceOrigin: req.headers.referer || req.headers.origin

Dropped: localhost, 127.0.0.1, ::1, *.local, 192.168.*, 10.*, tunnels, and
Vercel preview deployments. Dropped messages are still RECORDED and visible in
the dashboard — they are just never sent and never counted against quota.

Your production hostnames live on YOUR project row (`production_origins`, set
at registration or with the set_origins action above), merged with the
gateway's global PRODUCTION_ORIGINS. Register yours when you deploy, or your
real mail gets dropped too — no gateway redeploy needed.

If mail is vanishing, this is the first thing to check: the dashboard shows
those messages with status "dropped" and the reason.

--------------------------------------------------------------------------------
9. GOING LIVE SAFELY
--------------------------------------------------------------------------------
  1. EMAIL_GATEWAY_MODE=off      nothing changes; your old sender still runs.
  2. EMAIL_GATEWAY_MODE=shadow   your old sender still actually sends; the
                                 gateway records what it WOULD have done.
                                 Leave it here for about a week and compare.
  3. EMAIL_GATEWAY_MODE=on       the gateway sends.

  Rollback is setting the var back to `off`. No code change, no gateway
  redeploy. If you are migrating an existing project, pass your current sender
  as `legacy` so infrastructure failures fall back to it automatically:

    createEmailClient({ ..., legacy: (payload) => oldSendMail(payload) })

--------------------------------------------------------------------------------
10. WHEN SOMETHING DOES NOT ARRIVE
--------------------------------------------------------------------------------
  Dashboard          https://email-services-nu.vercel.app/            queue, quota, recent messages
  One message        GET  /api/v1/messages/:id     status, provider id, events
  Health             GET  /api/v1/health           queue depth, oldest pending
  Quota              GET  /api/v1/quota            what is left, by priority

  Check in this order:
    status "dropped"     -> your sourceOrigin was not a production host.
                            This is the most common cause. Register the
                            hostname (section 1) and it works.
    status "suppressed"  -> that address bounced, complained or unsubscribed
    status "throttled"   -> an identical alert went out inside the cooldown
    status "failed"      -> the transport refused; read last_error. It is
                            retried automatically by later traffic.
    no record at all     -> your project never reached the gateway. Check the
                            key, the URL, and EMAIL_GATEWAY_MODE.
